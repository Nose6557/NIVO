# Система рівнів

Як NIVO визначає рівень гравця, звідки беруться дані і які пороги на що впливають.

## Коротко

Кожне питання має поле `level` (`B1` або `B2`). Рівень гравця — це не середня оцінка по всьому банку, а **точність на питаннях цільового рівня**. Поки таких відповідей мало, рівень вважається невизначеним і бейдж не показується.

---

## 1. Розмітка банку

Поле `level` лежить у кожному питанні, одразу після `topic`:

```json
{
  "id": "cond-third-01",
  "topic": "cond-third",
  "level": "B2",
  "type": "mcq",
  ...
}
```

**Рівень призначається темі, а не окремому питанню.** Тема — це граматичний пункт, і складність є властивістю пункту. Усі питання однієї теми успадковують її рівень. Якщо колись знадобиться виняток, `level` можна перевизначити в конкретному питанні — резолвер це передбачає.

Дозволені значення оголошені в `banks/index.json`:

```json
"questionLevels": ["A2", "B1", "B2", "C1"]
```

Це впорядкована драбинка. Зараз реально використовуються лише `B1` і `B2`; `A2` та `C1` оголошені наперед, під майбутній контент і під тест на визначення рівня.

### Поточний склад банку

144 питання: **98 B1**, **46 B2**.

Категорії `articles`, `agreement`, `spelling`, `word formation` не містять B2 узагалі. Це не помилка розмітки — ці теми прийшли з паку особистих помилок, а він за визначенням складається з базових речей, які не закріпились.

### Резолвер

`app.js` збирає рівень за ланцюжком:

```js
q.level || pack.level || meta.level || null
```

Тобто рівень пака (`"B1-B2"`) лишається запасним варіантом, але поки всі питання протеговані, він не спрацьовує.

---

## 2. Валідація

`check.html` не дасть опублікувати банк, якщо:

- у питання **немає** `level` — воно б випало з фільтра рівнів і з тесту;
- значення `level` **немає в драбинці** `questionLevels`;
- в `index.json` **немає** самого `questionLevels`.

Плюс два попередження, які не блокують публікацію, але сигналять про перекіс:

- рівень має менше **30** питань — для чесного визначення цього замало;
- рівень займає менше **20%** банку — сесії цього рівня швидко почнуть повторюватись.

---

## 3. Обчислення рівня (`level.js`)

### Звідки дані

Таблиця `answers` у Supabase **не зберігає рівень**. Вона зберігає `question_id`, і рівень підтягується з банку за цим id через мапу `LEVEL_BY_ID`.

Наслідок: рівень рахується і по історії, накопиченій **до** появи цієї системи. Міграція SQL не потрібна — жодна колонка не додавалась.

Єдина зміна в `store.js` — у `loadProgress` додано `question_id` до списку колонок, бо раніше він не витягувався.

### Алгоритм

```
1. Відібрати з історії всі відповіді на питання рівня B2, відсортувати за часом.
2. Якщо їх менше 30 — рівень НЕВІДОМИЙ. Бейдж сховано. Кінець.
3. Взяти останні 30, порахувати точність.
4. Порівняти з порогами, врахувавши попередній вердикт.
```

### Пороги

| Параметр | Значення | Навіщо |
|---|---|---|
| `TARGET` | `B2` | рівень, який треба підтвердити |
| `BASE` | `B1` | підлога — нижче не опускаємось, бо A2-контенту немає |
| `WINDOW` | 30 | скільки останніх B2-відповідей беремо |
| `MIN` | 30 | менше — рівень невідомий |
| `UP` | 0.75 | поріг підвищення |
| `DOWN` | 0.60 | поріг зниження |
| `CONFIRM` | 2 | скільки перевірок поспіль мають бути вище `UP` |

### Гістерезис

Між 0.60 і 0.75 **нічого не змінюється**. Без цього рівень смикався б туди-сюди після кожної сесії й швидко знецінився.

### Подвійне підтвердження

Рівень перераховується після кожної сесії, і це створює храповик: він тільки росте, тож рано чи пізно щастить будь-кому. Симуляція на реальному складі банку при вікні 20 і одному підтвердженні:

| справжнє вміння | B2 через 20 сесій |
|---|---|
| 0.65 | **52%** ← хибне підвищення |
| 0.80 | 98% |

Вікно 30 плюс два підтвердження поспіль:

| справжнє вміння | через 12 сесій | через 20 |
|---|---|---|
| 0.50 | 0% | 0% |
| 0.65 | 17% | 25% |
| 0.72 | 50% | 69% |
| 0.80 | 88% | 97% |
| 0.90 | 100% | 100% |

Ціна — бейдж з'являється приблизно на 7-й сесії замість 4-ї.

Залишкові 25% хибних підвищень на 0.65 — межа самого методу повторюваних вимірювань. Прибирається підняттям `UP` до 0.80, але тоді справжній 0.80 отримуватиме B2 лише через раз.

### Ідемпотентність

Стан зберігається в `localStorage` під ключем `nivo.level`:

```json
{ "level": "B1", "up": 1, "seen": 42 }
```

`seen` — кількість B2-відповідей на момент останньої перевірки. Якщо число не змінилось, лічильник підтверджень **не рухається**. Тому перезавантаження сторінки не наближає підвищення.

### Відоме обмеження

Вердикт живе в `localStorage`, тож **не синхронізується між пристроями**. З іншого браузера відлік почнеться з `B1`, хоча точність перерахується з реальної історії й повернеться до правильного значення за дві сесії. Якщо це заважатиме — переносити в `profiles`.

## 4. Бейдж

Розмітка — всередині кнопки аватара:

```html
<button class="avatar-btn" id="avatar-btn">
  <span id="avatar-initial"></span>
  <span class="level-badge" id="level-badge" hidden></span>
</button>
```

Кольори з палітри гартування: **B1 — `--bronze`**, **B2 — `--blue`** (той самий колір, що означає майстерність у смужках категорій). Перемикається через `[data-level="B2"]`.

`pointer-events:none` — клік проходить крізь бейдж на кнопку, дропдаун відкривається як раніше. Підказка при наведенні висить на самій кнопці.

Коли рівень невідомий, бейдж отримує `hidden`. Не «—», не сірий кружечок: порожній бейдж читається як зламаний, а фальшивий `B1` знеціниться в момент, коли система пізніше скаже `B2`.

Перерахунок відбувається в `renderLevelBadge()`, яку викликає `renderHome()`. Тобто підвищення видно одразу після повернення на головну.

---

## 5. Порядок підключення

```html
<script src="store.js"></script>
<script src="level.js"></script>   <!-- має бути ДО app.js -->
<script src="app.js"></script>
```

`level.js` кладеться в корінь, малими літерами. GitHub Pages чутливий до регістру.

---

## 6. Що далі

**Вибір рівня.** Фільтр пулу питань плюс `profiles.level_pref` зі значеннями `B1` / `B2` / `auto`. В режимі `auto` — 70% питань свого рівня і 30% наступного. Саме ці 30% дають дані для підвищення: без них система ніколи не побачить, що гравець уже готовий.

Перед цим бажано, щоб друга партія питань була переважно B2 — 46 питань це три сесії до повного повтору.

**Тест на визначення рівня.** 15 питань драбинкою замість фіксованого набору: старт з B1, три правильні поспіль — крок вгору, дві помилки — вниз. Рівень, на якому стабілізувався, і є результат.

Результат виставляється через `Level.reset("B2")` — функція вже є.

Відповіді з тесту слід писати в `answers` з прапорцем `mode: 'placement'`, але **не** в `weak_items`: у тесті питання навмисне подаються поза зоною комфорту, і слабкі теми забруднив би шум.

## API

```js
Level.compute(answers, levelById)
// -> { level, accuracy, counted, needed, changed }
//    level:    "B1" | "B2" | null (null = невідомо, ховати бейдж)
//    accuracy: точність у вікні, 0..1
//    counted:  скільки всього B2-відповідей в історії
//    needed:   скільки ще треба до MIN
//    changed:  новий рівень, якщо щойно змінився, інакше null

Level.progressToNext(state)  // 0..1, або null якщо рівень цільовий/невідомий
Level.reset(level)           // виставити вердикт напряму (для тесту)
Level.CFG                    // усі пороги
```

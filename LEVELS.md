# Рівень гравця

Як NIVO визначає і тримає рівень. Уся модель — у `level.js` (рахує, нічого не малює),
вхід у неї — `onboard.js` (самооцінка й тест), споживач — `app.js` (бейдж, меню, добір
питань).

---

## Драбинка

```
A1 → A2 → B1 → B2 → C1 → C2
```

Рівень — **одне значення**, не вектор і не бал. Самооцінка й тест лише ставлять
стартову точку, далі значення безперервно коригують реальні відповіді. Рухається
воно тільки на сусідній щабель: перестрибувати нема на чому, бо питання поза
поточним рівнем гравцеві не даються.

Звідки взялося значення (`source`), визначає, наскільки швидко адаптив має право
його виправити.

## Що годує метрику

Точність рахується **лише по питаннях поточного рівня** — міра одна: «чи тягнеш
ти свій рівень». Відповіді сусідніх рівнів у вікно не потрапляють.

Питання з паку, позначеного `"scored": false`, **не рахуються взагалі**: `app.js`
не кладе їх у мапу `LEVEL_BY_ID`, тож для `level.js` їх ніби немає. Причина — лексика
на впізнавання значно легша за граматичну продукцію: у спільній метриці вона
завищувала б точність, і адаптив підіймав би рівень безпідставно. Той самий пак
виключений і з тесту рівня (`testable()` в `onboard.js`).

## Пороги

| Константа | Значення | Що означає |
|---|---|---|
| `UP` | `0.82` | точність вікна, з якої починається рахунок підвищень |
| `FAST_UP` | `0.92` | різке відхилення вгору — підвищуємо одразу |
| `DOWN` | `0.52` | точність, з якої починається рахунок знижень |
| `FAST_DOWN` | `0.35` | різке відхилення вниз — знижуємо одразу |

Пороги двоярусні навмисно. Помірне відхилення вимагає підтверджень, різке
виправляється з першого вікна: людина, посаджена не на свій рівень, потрапляє на
правильний швидко, а та, що вже на своєму, не смикається від однієї невдалої сесії.

## Довіра до джерела

| `source` | Звідки | `window` | `min` | `confirmUp` | `confirmDown` |
|---|---|---|---|---|---|
| `self` | самооцінка в онбордингу | 15 | 15 | 1 | 2 |
| `placement` | тест рівня | 20 | 20 | 2 | 3 |
| `manual` | вибір зі списку в меню | 20 | 20 | 2 | 3 |
| `adaptive` | сам адаптив | 30 | 30 | 2 | 3 |

- `window` — скільки останніх відповідей рівня беруться в розрахунок точності.
- `min` — скільки відповідей рівня взагалі має бути, щоб щось рахувати.
- `confirmUp` / `confirmDown` — скільки вікон поспіль мають перевищити поріг.

Слабша гіпотеза виправляється швидше: самооцінку достатньо спростувати одним
вікном, власне рішення адаптива — двома і на вдвічі довшій дистанції. Зниження
всюди вимагає на одне підтвердження більше за підвищення — це захист від
тимчасового спаду форми. Невідоме джерело трактується як `adaptive`.

## Неперекривні вікна

Підтвердження рахуються тільки на **свіжих** відповідях. У стані лежить `seen` —
скільки відповідей рівня було на момент минулої оцінки; наступна відбудеться, коли
їх стане більше ще на цілий `window`.

Без цього «два підтвердження поспіль» були б однією й тією ж вибіркою, порахованою
двічі, і рівень скакав би від шуму.

## `seen: null` — перебазування

`null` означає «точку відліку ще не поставлено». Такий стан виникає щоразу, коли
рівень задано ззовні: онбординг, тест, ручний вибір, профіль із сервера, міграція
формату. На першому ж `compute` туди записується поточна кількість відповідей рівня,
і далі чекаємо повне свіже вікно.

Нуль тут не годиться: у людини з історією вже можуть бути сотні відповідей цього
рівня, і рівень поїхав би від старої історії, без жодної нової сесії.

## Фіксація і оцінка

Перемикач «Автоматичний рівень» у меню аватара керує прапорцем `locked`
(увімкнено = `locked: false`). Коли рівень зафіксовано, `compute` рахує точність,
просуває `seen`, але **рівень не змінює**.

Щоб фіксація не була сліпою, поруч показується `estimate` — чесна оцінка: один щабель
від поточного рівня за свіжою точністю, без лічильників підтверджень і без запису
в стан.

```
acc >= UP   і не стеля  → щабель вище
acc <= DOWN і не підлога → щабель нижче
інакше                   → поточний рівень
```

Далі, ніж на щабель, оцінити нічим: питань інших рівнів гравець не бачить.
`estimateReady` каже, чи оцінці можна вірити — вона `false`, поки відповідей менше
за `min`, одразу після перебазування і одразу після зміни рівня (там точність
порахована на питаннях старого рівня, для нового вона нічого не означає).

## Стан і міграції

Стан лежить у `localStorage` під ключем `nivo.level`, поточна версія формату — `4`.

```json
{ "v": 4, "level": "B2", "source": "adaptive", "up": 0, "down": 0, "seen": 118, "locked": false }
```

| Ситуація | Що робимо |
|---|---|
| Немає поля `v` | стара B1/B2-схема: рівень зберігаємо, `source` = `adaptive` (він напрацьований відповідями), лічильники в нуль, `seen: null`, `locked: false` |
| `v` не збігається з поточною | рівень зберігаємо, лічильники в нуль, `seen: null` |
| Зламаний JSON або недоступний `localStorage` | порожній стан, без винятку назовні |

Бамп версії означає, що змінився сам набір питань, які годують метрику (у `v4` перестали
рахуватися паки `"scored": false`). Старий `seen` рахував іншу популяцію відповідей
і тепер завищений: реальних оцінюваних відповідей стало менше, ніж записано, умова
неперекривних вікон не виконалася б ніколи — і рівень замерз би назавжди. Тому `null`.

## Синхронізація з профілем

`hydrate(profile)` сіє стан із Supabase — **сервер завжди виграє над локальним**:

- `level` ← `profiles.level`;
- `source` ← `profiles.level_source`, якщо таке джерело відоме, інакше `adaptive`;
- `locked` ← `profiles.level_locked`;
- лічильники в нуль;
- `seen` зберігається, тільки якщо серверний рівень збігся з локальним, інакше `null`.

Якщо колонок рівня в базі ще немає, `store.js` тихо вимикає синхронізацію і рівень
живе локально.

## Добір питань

`levelPool()` в `app.js` вирішує, з чого збирати сесію:

1. Питання поточного рівня — якщо їх щонайменше `SESSION_LEN * 2` (30).
2. Інакше рівень і обидва сусідні — якщо разом набирається хоча б `SESSION_LEN` (15).
3. Інакше весь банк.

Поріг у дві сесії потрібен, щоб питання не почали повторюватися в межах одного вечора.
Обидва пом'якшення пишуть причину в консоль.

Далі `buildQueue()` зважує пул за частотою помилок у темі (тема без історії важить
`0.35`) плюс випадковий доданок до `0.5` — так слабкі місця випадають частіше, але
сесія не стає однаковою.

## Тест рівня

`onboard.js`, `TEST_LEN = 16`, лише питання типу `mcq` з паків, що годують метрику.

Метод зважений сходинковий. Оцінка `est` — дробова позиція на драбинці, стартує
з середини доступного діапазону рівнів:

| Крок | Значення |
|---|---|
| `STEP_UP` | `0.43` |
| `STEP_DOWN` | `1` |

Кроки несиметричні навмисно: симетричні сходилися б до рівня, де людина відповідає
на 50%, а «свій рівень» — це ~70%. Пропорція `(1 − 0.7) / 0.7` і дає `0.43`.

Перші **чотири** питання йдуть повним кроком, з п'ятого масштаб `0.5`: спочатку
швидко звузити діапазон, потім точно довести. Після кожної відповіді `est`
підрізається до `[lo − 1, hi + 1]` — так виявляється рівень, під який контенту
ще немає.

Питання беруться з найближчого до `round(est)` рівня, де ще лишилися невикористані.
Правильна відповідь під час тесту **не показується**: інакше це навчання, а не вимір —
людина калібрується по ходу, і результат зміщується.

Підсумок — `ORDER[clamp(round(est))]`, далі `Level.setPlacement()`. Якщо придатних
питань у банку немає взагалі, тест завершується рівнем `B1` із джерелом `self`.

Самооцінка — п'ять формулювань без згадки CEFR, від A1 до C1. `C2` через самооцінку
не дається: його треба підтвердити тестом або грою.

## API

```js
Level.compute(answers, levelById)   // головний розрахунок, пише стан
Level.current()                     // поточний стан без розрахунку
Level.hydrate(profile)              // засіяти з профілю Supabase
Level.setSelf(lv)                   // самооцінка       → source "self"
Level.setPlacement(lv)              // результат тесту  → source "placement"
Level.setManual(lv)                 // вибір у меню     → source "manual"
Level.setLocked(on)                 // фіксація рівня
Level.progressToNext(state)         // 0..1 до наступного щабля, null на стелі
Level.reset()                       // порожній стан
Level.ORDER, Level.CFG              // драбинка і константи
```

`compute(answers, levelById)` приймає рядки відповідей (`question_id`, `is_correct`,
`answered_at`) і мапу `id питання → рівень`, а повертає:

| Поле | Що це |
|---|---|
| `level` | рівень після розрахунку |
| `source` | джерело значення |
| `accuracy` | точність вікна, `null` поки відповідей менше за `min` |
| `counted` | скільки всього відповідей цього рівня враховано |
| `needed` | скільки ще потрібно до найближчої оцінки |
| `changed` | `null` або `{ from, to, dir: "up" \| "down" }` |
| `estimate` | чесна оцінка рівня |
| `estimateReady` | чи можна вірити оцінці |

`changed` — єдиний сигнал для інтерфейсу: підвищення `app.js` святкує повноекранно,
зниження показує тихим тостом про зміну складності. Асиметрія навмисна — демоція
демотивує за визначенням, тому вона говорить про контент, а не про статус людини.
